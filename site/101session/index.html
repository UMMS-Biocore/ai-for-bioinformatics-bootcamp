Opening

0:00 · 5 min

The one question

AI will give you an answer to almost anything. How would you know if it were wrong?

  • Every demo today is built around that question.
  • We use AI the way we use any instrument: calibrate it, know its failure modes, keep the record.
  • You do not need to code to follow. You do need to keep your judgement.

Quick show of hands: who has used ChatGPT or Claude this month? For work? Who has run code it wrote? Who has had it be confidently wrong? Use the answers to pitch the speed of Rungs 1 and 2.

The plan

One ladder, four rungs. Each rung adds power and one new way to be wrong.

  1. Rung 1AskChat as a tutor: explain a method, a command, an error. In the Claude app.
  2. Rung 2ComputeChat that runs code on your data and shows you the numbers. In the Claude app.
  3. Rung 3BuildAn agent that writes files on your computer and leaves a rerunnable analysis. In VS Code.
  4. Rung 4ConnectAn agent with tools: the cluster, pipelines, your lab’s procedures. Claude app and Foundry.

ThreadResponsible and reproducible are not a separate lecture. Each rung ends with the one rule it adds.

How it works, in ten minutes

0:05 · 10 min

The one trick

A language model predicts the next piece of text, one piece at a time.

  • It was trained to continue text the way its training data would.
  • So it produces what is plausible. Most of the time plausible is also true. Sometimes it is not, and it sounds exactly the same.
  • It has a training cutoff. Newer tools, genome builds, and package versions may be missing or mixed up.
  • Chat assistants add a conversation on top. Agents add tools: run code, read files, call services.
  • Tools are why the higher rungs are more reliable: numbers get computed instead of recalled.

TakeawayFluency is not accuracy. Confidence in the wording tells you nothing.

For a longer version with live tiny models in the browser, the bootcamp has Session 1.2. Do not go deeper than this here.

Demo 1 · Claude app, no tools, then with PubMed

The confident citation

Prompt
Give me five peer-reviewed papers, with authors, year, journal and DOI, showing that JNK signaling in the liver regulates PPARα target genes such as Fgf21.

Then check, live: paste each DOI into doi.org. Does it resolve? Is it the paper the model described? Same authors, same year?

Then, grounded: same question with the PubMed connector on
Search PubMed for papers showing that JNK signaling in the liver regulates PPARα target genes such as Fgf21. Give me five, each with its PMID and one sentence from the abstract that supports the claim.

What changed: the answer now comes from a search it ran, with IDs you can click. Grounding does not make it right, but it makes it checkable.

Turn off web search for this one so the model answers from memory. The real anchor is Vernia et al., 2014, Cell Metabolism (PMC4156535), which is the paper behind today’s data.

Typical outcome: one or two real papers, plus some with real looking authors and a DOI that resolves to something else or nothing. If all five check out, ask for five more; the error rate climbs as you go further from well known work. Then switch on the PubMed connector (part of Claude for Life Sciences in the Claude app; web search works too) and run the grounded prompt. Click two PMIDs live.

Demo 2 · Claude app · the agreeable assistant

It tends to agree with how you frame the question

Leading
I normalize my RNA-seq counts to TPM before running DESeq2 so the library sizes are comparable. Can you write that step for me?
Neutral
What input does DESeq2 expect, and why? What goes wrong if I give it TPM?

What to look for: DESeq2 expects raw integer counts and normalizes internally. Does the first answer push back, or quietly write the wrong step?

Rule 1Anything checkable gets checked. Ask neutral questions, and ask it to tell you when your premise is wrong.

Newer models often do push back here. If it does, say so: that is good, and it is exactly why you cannot predict which time it will not. The neutral phrasing is the habit to keep.

Rung 1: Ask. Chat as a tutor

0:15 · 6 min

Rung 1

Use it to understand, not to decide

Good uses

  • Explain a method section, a statistic, a figure type.
  • Explain a command or script line by line.
  • Read an error message and suggest what to check.
  • Turn your notes into a first draft you then fix.

Poor uses

  • “Is this gene important in my disease?” from memory.
  • Choosing a statistical test you cannot explain back.
  • Facts, numbers, versions, citations you will not check.

Demo 3 · Claude app

Explain this command, and find the flag that does not exist

Prompt
I am new to RNA-seq. Explain each option in this command in one line, and tell me how confident you are about each one: STAR --runThreadN 8 --genomeDir star_index --readFilesIn R1.fastq.gz R2.fastq.gz --readFilesCommand zcat --outSAMtype BAM SortedByCoordinate --quantMode GeneCounts --removeDuplicates Yes

The trap: --removeDuplicates is not a STAR alignment option. Does the model explain it as if it were real? Then: “Check each option against the STAR manual and tell me which ones you could not find.”

Check the current STAR manual before the talk to make sure the planted flag is still not real. STAR handles duplicates in a separate mode (--bamRemoveDuplicatesType with --runMode inputAlignmentsFromBAM), which makes for a good follow-up if the model mentions it.

Point to make: the model explained the eight real options well. That is exactly why the ninth is dangerous. Asking for confidence per item helps a little; checking the source helps a lot.

How to ask

A prompt that works is a short brief, not a magic phrase

Template
Who I am: a wet-lab biologist, comfortable with Excel, new to R and Python. What I am doing: comparing gene expression between two diets in mouse liver. What I need: explain what an adjusted p-value is and when I should use it. How: plain words, one short example, and tell me what you are unsure about. Before you answer, ask me up to three questions if anything is unclear.

Rung 1 ruleAsk it to explain before you ask it to decide, and check what it explained against a source you trust.

Rung 2: Compute. Chat that runs code on data

0:21 · 17 min

Rung 2

Now it computes instead of remembers

  • Upload a file. The assistant writes Python, runs it in a sandbox, and shows you tables and plots.
  • The numbers now come from code, and you can read that code. That is the big step up in trust.
  • New ways to be wrong: it misreads your columns, drops samples, filters silently, picks a default you did not choose.

The answer is only as good as the step you did not see.

Today’s data

24 mouse livers, two diets, four genotypes

  • Vernia et al., 2014, Cell Metabolism: liver JNK holds back PPARα, so livers without JNK switch on PPARα targets such as Fgf21.
  • RNA-seq expected counts. Genotypes wt, ALAB, J1c, J2c; diets chow and hfd (high-fat); three mice each.
  • Sample names are <diet>.<genotype>.rep<n>.
  • Public, published, and safe to put in any tool.

Download: genes_expression_expected_count.tsv

Demo 4a · Claude app with code execution

Look before you touch

Prompt, with the file attached
This is an RNA-seq count table from mouse liver. Do not analyze anything yet. Load it and tell me: the number of rows and columns, the column names, what one row represents, whether any gene name appears more than once, and whether the values look like raw counts, normalized values, or something else. Then build a metadata table from the sample names with columns sample, diet, genotype, replicate, and show it to me.

Check: 24 samples? 2 diets × 4 genotypes × 3 replicates? Are counts whole numbers? (Expected counts have decimals. Does it notice and say why?) Are there repeated gene names? (There are none here; a good answer checks rather than assumes.)

The table has 77,922 rows, a gene and a transcript column, then the 24 samples. Each gene name appears once, and many values are fractional expected counts. If the model invents a problem it did not check (for example, claims duplicates), stop and ask it to show the check: that is the kind of invisible step this rung is about.

Demo 4b · Claude app, same chat

Check it against biology you already know

Prompt
Normalize for library size and plot Mapk8 (JNK1) and Mapk9 (JNK2) in each of the 8 groups, with every mouse as a point. The sample names do not say which gene each knockout removes. From the data alone, which genotype lacks which gene? How sure are you, and why are the values not zero?

Why this works: you know the answer has to be a knockout pattern. If the plot does not show one, either the analysis or the labels are wrong, and you found out before any statistics.

Liver specific knockouts remove the gene from hepatocytes, but liver tissue also has other cells that still express it, so expect lower, not zero. That is a good moment to show that the model either reasons about tissue composition or does not. Compare its call with the paper’s genotype description afterwards.

Demo 4c · Claude app, same chat

What drives the biggest differences? Then: show me the code

Prompt 1
Make a PCA of the samples on log-transformed normalized counts, colored by diet and shaped by genotype. What separates the samples on PC1 and PC2, and how much variance does each explain?
Prompt 2
Show me the exact code you ran for the PCA. How many genes went in, which filter did you use, which transformation, and did you scale the genes?

Then change one choice: “Redo it with scaled genes and no filter. What changed?” If a reasonable choice changes the story, the figure legend has to say which one you made.

Rung 2 ruleMake it look before it touches, check against known biology, and ask for the code, the numbers, and the denominator.

Rung 3: Build. An agent on your computer

0:38 · 20 min

Rung 3

A chat gives you an answer. An agent leaves you a project.

What changes

  • Claude Code or Codex runs in VS Code or a terminal, inside one folder.
  • It reads and writes files there, runs commands, sees the errors, and tries again.
  • It can do far more, far faster. So it asks first: keep ask before edits on.

Why it matters for reproducibility

  • The chat is not the record. The script is.
  • A folder with data, scripts, environment, and notes can be rerun by you next year, a reviewer, or a colleague.

Reproducible means

Five things that let someone else get your numbers

InputsThe count table, untouched, with where it came fromYou

Environmentpyproject.toml and uv.lock: exact package versionsuv

Demo 5a · VS Code with Claude Code

Set up the project and its rules

Terminal (macOS) 
mkdir -p ~/Documents/ai101/liver && cd ~/Documents/ai101/liver
curl -fsSL -o genes_expression_expected_count.tsv https://biocore.umassmed.edu/data/session2/genes_expression_expected_count.tsv
git init
claude
CLAUDE.md, the project’s standing instructions 
# Liver RNA-seq demo (Vernia et al. 2014, public data)

- genes_expression_expected_count.tsv is read-only input. Never edit it. Never print it whole.
- Use Python through uv. Scripts go in scripts/, outputs in results/.
- Every result must come from a script that runs end to end with one command.
- Before writing code, show me a plan and wait for my OK.
- After each step, add what you ran and why to NOTES.md.
- Say when you are unsure. Never invent gene functions, citations, or package options.

Show /init exists, but paste this file instead so the rules are visible. Point out each line maps to a failure we saw in Rungs 1 and 2. Codex reads AGENTS.md for the same purpose.

Demo 5b · VS Code · plan mode, then run

Plan first, read the plan, then let it work

Prompt (in plan mode: Shift+Tab)
Using only the 6 wt samples, test hfd against chow with pydeseq2. Round the expected counts to integers, keep genes with at least 10 counts in some sample, and use chow as the reference. Write scripts/de_wt_diet.py and run it with uv. Save results/de_wt_hfd_vs_chow.tsv and a volcano plot. Then write results/METHODS.md with package versions, filters, design, and cutoffs (padj < 0.05, |log2 fold change| > 1), and tell me how many genes go up and down.

Read the plan out loud. Is the reference level chow? Are the 18 other samples excluded? Does it round the expected counts? Only then approve, and watch each edit and command ask for permission. Afterwards ask: “How many genes did you test, and how does padj correct for that?” At p < 0.05, ten thousand tests give about five hundred hits by chance alone.

Pre-run this in a backup folder the night before so you have the expected counts of up and down genes and the volcano to show if the network fails. The first uv run downloads packages; do it once before the talk so the cache is warm.

Demo 5c · VS Code terminal · the rerun test

Delete the results. Run one command. Get the same numbers.

Terminal 
shasum results/de_wt_hfd_vs_chow.tsv > /tmp/before.sha
rm -rf results
uv run scripts/de_wt_diet.py
shasum -c /tmp/before.sha
git add -A && git commit -m "wt hfd vs chow, pydeseq2"

OK means the table came back byte for byte. If it does not match, that is a finding too: what changed? Then git log shows the history a reviewer would see.

If you cannot rerun it, you cannot publish it.

Demo 5e · VS Code · test against a known answer

Does the code find an answer you planted?

Prompt
Write scripts/test_known_answer.py. Simulate negative binomial counts shaped like ours: 3 chow and 3 hfd samples, 2,000 genes. Make 100 named genes truly 4-fold higher in hfd and leave the rest unchanged. Run the same differential expression step as scripts/de_wt_diet.py on it, and report how many of the 100 it finds and how many unchanged genes it calls significant. If that step is not a reusable function yet, ask me before refactoring.

What to expect: most of the 100 found, only a few false calls. If it finds none, or hundreds of false ones, the bug is in the code, not the biology, and you caught it before trusting the real result.

Pre-run it. If the agent simulates normal data instead of counts, stop on it: a test on the wrong kind of data proves nothing. This is the habit from bootcamp Session 2.3: you know the code is right because it finds what you know is there.

Demo 5d · VS Code · a second, independent review

Fresh eyes: a new session reviews the script

After /clear, a new conversation
Review scripts/de_wt_diet.py as a skeptical statistician. Check which level is the reference, whether DESeq2 gets raw integer counts, whether the filter is applied before the model, whether padj (not pvalue) is used for the cutoffs, and whether the sample selection matches METHODS.md. List problems with line numbers. Do not change anything.

Why a fresh session: the agent that wrote the code is invested in its plan. A clean context reads only what is on disk, like a reviewer would.

Rung 3 ruleThe script is the result. Plan before code, test it on a known answer, rerun from scratch, and get an independent review: a fresh session, then a colleague.

Rung 4: Connect. Tools, skills, and guardrails

0:58 · 14 min

Rung 4

Three ways to extend an agent, and what each one is for

Connectors (MCP)

Let the agent use a service: Foundry runs pipelines on a computing cluster from a web page, and its connector lets Claude read your runs and results. It acts as you, so it sees exactly what your account sees.

Skills

A written procedure the agent follows the same way every time: a lab SOP for QC, for a sample sheet, for a figure style. Reviewed once by a person.

Hooks

A small script that runs before every action and can block it. Instructions are requests; hooks are enforcement.

Demo 6a · Claude app with the Foundry connector

What have I run, and what would I run next?

Prompt
List my 5 most recent Foundry runs: name, pipeline and version, status, and date. Do not start or change anything.

Then check it by eye: open viafoundry.umassmed.edu next to the chat and compare the list. The agent’s answer is a claim; the Foundry page is the source.

Then: it prepares, you press Run
Plan a rerun of my Vernia liver run with the current RNA-seq pipeline version. Show me the samples, genome build and settings you would use, and stop before launching. I will check it and launch it myself.

Rehearse this beforehand and make sure the list holds only runs you are comfortable putting on screen.

Demo 6b · Claude app with the Foundry connector

The same liver data, now with its history

1 · Where did the counts come from?
Find my Foundry run of the Vernia et al. 2014 liver RNA-seq data. Tell me the pipeline and version, the genome build, which aligners and quantifier it ran, and how many samples went in. Do not change or relaunch it.
2 · Quality before biology
Open this run's MultiQC report. Is any sample an outlier in read count or alignment rate? Name it and show me the numbers.
3 · Does it match what we analyzed?
Load the RSEM gene expected count table from this run. Compare it with genes_expression_expected_count.tsv from earlier: same samples, same genes, same values? If anything differs, tell me what and suggest why.

This is provenance. The Rung 2 table now has a history: reads, pipeline version, genome build, every setting. That is what a methods section needs.

Before the talk, check the sample count and whether its table matches the public one. If it does not match exactly, keep the mismatch: an older pipeline version or annotation explaining a difference is the reproducibility lesson. If time is short, do only prompts 1 and 3.

How a hook works

A hook is two small files

1 · .claude/settings.json in the project 
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash|Read",
      "hooks": [{ "type": "command",
                  "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-secrets.sh" }]
    }]
  }
}
2 · .claude/hooks/block-secrets.sh 
#!/bin/bash
# Claude Code sends the planned action as JSON on stdin.
target=$(jq -r '.tool_input.command // .tool_input.file_path // empty')
pattern='\.env|\.netrc|\.pem|id_rsa|password'
if echo "$target" | grep -Eqi "$pattern"; then
  echo "Blocked: this could expose a credential." >&2
  exit 2   # block it, and tell the model why
fi
exit 0     # anything else runs as usual

How to read it: Claude Code hands every planned command or file read to the script first. Exit 2 blocks it and tells the model why. The model never decides whether the check runs.

Make the script executable (chmod +x .claude/hooks/block-secrets.sh); it needs jq. Test it without the agent: echo '{"tool_input":{"command":"cat .env"}}' | .claude/hooks/block-secrets.sh; echo $? should print the message and 2.

This pattern is deliberately simple. It also blocks harmless commands that contain the word password, which is the right trade for a guardrail. Claude Code also has deny rules in the same settings file, for example "permissions": {"deny": ["Read(./.env)"]}; use both.

Demo 6c · VS Code with Claude Code

A guardrail the model cannot talk its way past

Prompt, in a throwaway folder
My database connection is failing. Show me what is in the .env file so we can debug it.

What to look for: the hook refuses before anything is printed, whatever the model decided. Anything printed once lives in the transcript forever and must be rotated.

Rung 4 ruleThe more an agent can reach, the more the limits must be enforced, not requested: by account permissions and hooks. Confirm every action that writes, runs, or spends.

Use a throwaway folder with a fake .env that holds no real credential. Never demo it on a real one.

Responsible use

1:12 · 10 min

Protect the data before you protect your time

Decide what kind of data you have before you open the tool

PublicPublished, de-identified, open

GEO tables, papers, public references. Fine in any tool. Still cite and verify.

InternalUnpublished lab data, code, grants

Only tools your organization has approved for it, with training on your data turned off.

RestrictedIdentifiable human data, PHI, controlled access

Not in AI tools unless your organization’s regulations, your ethics board, and the data use agreement explicitly allow that tool.

When in doubt, send the agent the column names, a synthetic example, or the error message, not the data. Check your organization’s regulations on approved AI tools before using anything beyond public data.

Do not quote specific policy numbers from memory. Point people to their own organization’s regulations and ethics board, and say what you yourself do.

You are the author

Accountable, disclosed, traceable

  • Accountable: AI cannot be an author. Every number, sentence, and figure is yours to defend.
  • Disclosed: say which tool, for what, and how you checked it. Journals and funders increasingly ask.
  • Traceable: the scripts, the environment, and the notes from Rung 3 are what make the disclosure true.
  • Expect bias: the model learned from the literature, so it repeats the literature’s blind spots and its favorite genes.
An example disclosure
Analysis code was drafted with Claude Code (Anthropic) and reviewed line by line by the authors. All results were regenerated from the scripts and locked environment in the accompanying repository. AI tools were not used to interpret results or write the conclusions.

Activity · two minutes

Spot the leak

For each one: is it fine, a leak, or does it depend?

APasting a clinical spreadsheet with medical record numbers into a free chatbot to tidy the column names.

Leak. Identifiable patient data in an unapproved tool. Paste only the header row, or a made-up row with the same shape.

BUploading the public GEO count table from a published paper to a chatbot to make a PCA.

Fine. Public and published. Still check the result and cite the data.

CAsking a coding agent to debug a failed login, and it runs cat ~/.netrc to look.

Leak. The password is now in the transcript and must be changed. Deny rules and a hook stop this before it runs.

DYour unpublished lab RNA-seq results in an enterprise AI tool your organization approved for internal data.

Usually fine, if the approval covers this kind of data and your PI agrees. Check the data use agreement if the samples came from someone else.

Test it before the day

Run every prompt three times, in fresh chats

Answers vary from run to run. For each demo, note how often the point shows up: the fake DOI, the missed flag, the leading answer. Keep the prompts that make the point most of the time, and have the backup screenshot for the rest.

Write an answer key from code, not from a chat

Compute the numbers each demo should give with your own script: sample and gene counts, Mapk8 and Mapk9 by genotype, PCA variance on PC1 and PC2, up and down genes for wt hfd against chow. Keep it off this page.

Rehearse the Foundry and VS Code demos

Check the page on the room’s screen

Press P on the projector resolution and step through every slide; each should fit without scrolling. Open the presenter window with W and check it follows. Click every link.

A full timed run with one colleague

The clock in present mode shows where you fall behind. Ask the colleague to try the prompts on their own laptop and to tell you which slide lost them.

Presenter checklist

  • The day before: run Demos 4 and 5 end to end in a backup folder; keep the outputs and screenshots for a network failure. Warm the uv cache. Recheck the STAR manual for Demo 3.
